## 第4回実測（70分連続録音）の反映

### 確定したこと
- **クロックドリフトは無い。** ズレ ≒ 起動遅延 + Σ(underrun の欠損)。70分で1045回×6.9ms＝
  7.21秒に対し実測7.26秒。判定の決め手は「ドリフト換算は3回で9倍ばらつくのに、
  1回あたりの欠損は長い2本で10%差に収まった」こと。→ ADR-006。
- **ゼロ埋めは70分続く。** 穴は8個/81.8秒＝1.93%で、動画が止まっていた時間帯に固まっていた。
  ADR-004 は維持しつつ、`drops_sec_len` は「例外を拾う仕組み」と位置づけ直した。
- **70分の WAV は壊れない。** 自分405MB / 相手730MB。逐次書き出しは効いている。
  相手の RMS は70分ずっと -31±1 dBFS。運用の音量目安として REQUIREMENTS へ記録した。

### 直したもの（実測メモの分担どおり）
1. **バッファを既定から1秒へ**（`BufferSize::Fixed(rate)`、通らなければ既定へフォールバック）。
   cpal のソースのとおりコールバック周期は `GetDevicePeriod()` 固定なので、**遅延は増えず
   取りこぼしの余裕だけ増える**。停止後に処理するこのPJだから採れる手で、voice-input では採れない。
   **効果は未検証**。開発デスクトップでは1秒バッファが受理されることだけ確認した。
2. **先頭の空白を `drops_sec_len` に含めた。** 統合器が「サンプル0 = first_data_sec」と
   「それ以降の穴」の2つの原点を組み合わせる契約になっていたのを、`drops_sec_len` だけで
   復元できる形に変えた。誤差は約1バッファ。
3. **ズレの警告文言を系統で分けた。** 相手は「鳴っていた時間しか来ない」、自分は
   「起動遅延 + underrun」。同じ文言だと読み違える。実際に1回あたりの ms も出すようにした。

### 記録の整理
PROGRESS.md が59行/60行で上限に触れたため、**ADR を `docs/adr.md` へ移した**。
グローバル規約は「10件超で `docs/adr/`（1決定1ファイル）」だが、行数上限のほうが先に効いた。
7件なので単一ファイルにしている。増えたら分ける。

### STT の方針を決めた（ADR-007）
業務ノートの空きが3.4GB（うち今回の録音1.1GB）しかないため、**ビルドも Python も要らず
容量が最小の whisper.cpp ビルド済み CPU バイナリ**を第一手にした。
Vulkan 一式（SDK・Ninja・MSVC BuildTools・CMake）は数GB必要で入らない。
voice-input と同じエンジンなので結果が流用でき、速度が足りなければ GPU 化も同じ道を辿れる。

## 時刻ベースの統合器を実装（`proto/merge-transcript`）
`drops_sec_len` だけで WAV 内時刻 → 実時刻 を復元し、2トラックを突き合わせて
`自分:` / `相手:` のラベル付きトランスクリプトを出す。**WSL で動く**（音声デバイスに
触らないので Windows 側である必要がない）。

- 変換: 累積ラグ `L_i = Σ len`、段差の位置 `W_i = at_i − L_i`、`t_real = t_wav + L(t_wav)`。
  先頭の空白も `drops_sec_len` に入っているので、この配列だけで復元できる。
- 同じ話者が2秒以内で続く発話は1行にまとめる（whisper は文単位で切るので、
  そのままだと短い行の壁になり要約にも効かない）。
- ヘッダに補正量と空白の数を出す。統合が効いたかを一目で確かめるため。

### 踏んだバグ（実装中に発見・修正・テストで固定）
段差の位置を引き算で出すため丸め誤差が乗り、`10.500 − 9.800 = 0.7000000000000002` で
**境界ちょうどのセグメントが段差を1つ飛ばし、9.6秒ずれたまま静かに出力されていた**。
whisper の刻みが 10ms なのでセグメントは境界に乗りやすく、構造的に踏む。
例外も警告も出ず、出力は最後まで生成されて順序だけが間違う。
→ 1マイクロ秒の許容差を置き、`cargo test` に回帰テスト4件を入れた。

## 開発デスクトップに whisper.cpp を導入し、端から端まで通した

`ggml-large-v3-turbo-q5_0.bin`（574MB）。**業務ノートと同じモデル・同じ既定設定**なので、

### 実データでの検証
意図的に空白を作って録音（0-3秒 無音 / 3-23秒 再生 / 23-31秒 無音 / 31秒〜 再生）。
穴を2箇所とも拾い（3.16秒に3.16秒 / 31.61秒に8.23秒）、統合器は2本目を `[00:33.1]` に置いた。
**補正しなければ `00:21.8`** ＝ 11.4秒早い位置に出る。

### 危うく正しい実装をバグとして直すところだった

録音された WAV の該当区間を直接見たところ **-76〜-90 dBFS の暗騒音**で、音が鳴り始めるのは

「音が鳴り始めた時刻」ではない。**期待値のほうが間違っていた。**
→ 検算が合わない時、まず疑うべきは期待値。計算だけで詰めていたら実装を壊していた。

## 途中終了で録音を失う問題を潰し、配布形式の見通しを立てた

### 見つけた問題（実会議の前に出てよかった）
会議は長さが読めないので手で止めることになるが、**強制終了すると 1.7MB のデータが
書かれていても「not a WAVE file」で読めない**。hound が作成時にサイズ欄を 0 で書き、
`finalize()` で埋める作りのため。ヘッダを見ると形式は残っていてサイズ欄だけが 0 だった。

対処を3つ:
1. **秒数を省いたら止めるまで録り続ける。**会議はこれ。数字は計測のときだけ。
2. **Ctrl+C と Enter の2経路で止める。** Ctrl+C は環境によっては届かない
   （WSL から `kill -INT` を送っても CTRL_C_EVENT にはならない。実測で確認）。
   **止め方が1つだと、効かなかった時に全部失う。**
3. **`--repair`** でヘッダを直す。読めなくなった2本とも戻せた。
   ただし meta.json が無いので時刻の補正はできない。

### 配布形式の見通し（ADR-011）
`-C target-feature=+crt-static` でビルドすると **VC++ ランタイムへの依存が消え、
621KB の単一 exe** になることを確認した（既定ビルドは `VCRUNTIME140.dll` 等に依存）。
→ 業務ノートに置くのは exe 1つで足り、Rust も MinGW もリポジトリも要らない。
→ voice-input の `register.ps1`（スタートメニュー・自動起動・アンインストール登録）が流用できる。

**着手は実会議を数回通してから。**設定に何が要るか、ホットキーの形が実運用で決まるため。
ADR-002（配布しない）の前提「対象PCが pull できる」は、
**pull できることと業務PCにソースを置き続けたいことは別**、という形で崩れた。

## 【失敗と回収】ビルド生成物183MBをコミットしていた
配布用に静的リンクのビルド先を `target-static/` という別名で作ったが、`.gitignore` が
`target/` しか弾いておらず、226ファイル・183MB がコミットされていた。`.git` は 54MB。
業務ノート側からの指摘で判明。配りたかったのは実行ファイル1本（652KB）だけだった。

**原因は `git add -A` を、追加されるものを見ずに走らせたこと。**
`git status --short | head -3` で先頭3行しか見ておらず、226ファイルの追加が視界に入らなかった。
先頭数行だけ見る癖が、大量追加をちょうど隠す。

対処:
- `.gitignore` を `target/` + `target-*/` にした（名前ごとに足すのではなく接頭辞で押さえる）。
- `git filter-repo` で履歴から除去し、force push（グローバル §5 のとおり事前確認を取った）。
  **54MB → 328KB。**コミット17件は内容もメッセージも保持。
- 実行前に**スクラッチのクローンで試し**、結果を数字で確かめてから提案した。
- 実行前に `git bundle create --all` でバックアップ（45MB）。

`filter-repo` は安全策として `origin` を消すので remote を付け直した。
`bbe7139` 以降のハッシュが変わったため、**業務ノート側は `git reset --hard origin/main` が要る**。

> 履歴に入った大きなファイルは、後で消しても clone のたびに落ちてくる。
> 機械が2台・上に積まれたコミットが1つ、の段階で気づけたのが幸いだった。**早いほど安い。**

## VAD の評価（業務ノートの負の結果を追試）
業務ノートで「VAD は 48% 遅くなり、無音を削れていない」という結果が出た。
開発デスクトップは73倍速いので、既知の無音を 26.6% 入れたファイルで追試した。

### 測り方が違っていた
「出力セグメントの合計が元とほぼ同じ＝削れていない」と読んでいたが、**出力の
タイムスタンプは元の時間軸へ戻して返される**ので、何を削っても被覆は全体になる。
正しい数字はログの `whisper_vad: total duration of speech segments:`。
実際は 150.6秒 → 87.05秒（42%減）で、**削れてはいた**。

### それでも遅い理由と、業務ノートの読みの正しさ
処理量が42%減りエンコード窓が 7→4 に減ってなお総時間は増えた（GPU）。
**区間ごとの固定費が削減分を食っている。**「区間を減らせば勝てるのでは」という読みは
方向として正しく、`-vsd 1000` は区間を 35→6 に減らす（処理量は34%減を維持）。
エンコードが支配的な CPU では効く可能性がある。

### より重大な発見: VAD は語頭を削る
認識結果が壊れていた。「リポジトリ」→「ポジトリ」、「ホットキー」→「ストキー」、
「明日の」→「椅子の」、「議事録」→「疑似録」。前置きのパディング（既定30ms）が足りない。
`-vp 200` でほとんど戻るが完全ではない（400ms でも「リポジトリ」は戻らない）。

→ **本番では VAD を使わない。**実時間比 0.046 で速度は足りており、削る理由が無いのに
   品質を落とす取引になる。区間の数だけ語頭が壊れる。
→ 非常口で使うなら `-vsd 1000 -vp 200` を起点に CPU で実測する。
→ 幻聴の抑制は実会議の録音でしか評価できない。語頭の欠落と天秤にかける話になる。

> **速度の実験でも、出力そのものを並べて見る。**「速くなるか」だけを見ていたら、
> 語頭が落ちることに気づかないまま採用するところだった。
