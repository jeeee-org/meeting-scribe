## 第2回実測（Logi USB Headset H340 / 業務ノート）の受領と反映
`c1dc243` を業務ノートで pull → ビルド26.85秒で通り、**README だけで動かせる状態**になっていた。
引き継ぎの形（README に手順・目安・渡し方を書く）は機能したと言える。

### 直したバグ: 相手トラックの右チャンネルを捨てていた
902,813フレーム中879,369＝97.4%で L≠R だったのに 1ch に落として書いていた。
最初のチャンクだけで判定しており、それが0.333秒に届いた**モノラルの合図ビープ**だった。

**窓を広げても直らない**ことに注意した。本編の再生開始が10秒後なので、5秒の窓でも同じ
誤判定になる。会議の音はシステム全体の再生音（通知音・動画が混じる）でモノラルの根拠が無い。
→ **相手側は構造的にダウンミックスしない**（`downmix_allowed = false`）。
→ マイク側は残すが、判定を「無音でないフレームが0.2秒ぶん、かつ2秒ぶん見てから」に変更。
   材料不足のまま打ち切った場合は落とさない（安全側）。
→ 表示の文言も修正。`downmix_violations > 0` で「全chが同一だったため」と書くのは記録が偽になる。

`timeline_sec_frames` を小数3桁へ（式が崩れた時に場所を追える解像度）。

### 検証中に出た新しい事実: ゼロ埋めは同じ機械でも実行ごとに割れる
改修後の動作確認で、**開発デスクトップの NVIDIA HDMI がゼロ埋めしなくなった**
（最初のデータが3.22秒＝再生開始と一致）。過去2回の実行では0.01/0.03秒から埋まっていた。

「直前まで再生していたからエンジンが回り続けていた」という仮説を立てて実験したが、
**音を鳴らした直後に無音のまま6秒録ってもフレームは1つも来ず、否定された**。
他アプリが再生ストリームを開いたままだったのが原因と考えられるが特定できていない。

→ **ドライバ別の整理（NVIDIA はゼロ埋め / Realtek は来ない）を撤回した。**
→ ADR-004（時刻ベース統合）は「機種によっては必要」ではなく**常に必要**。強化された。
→ 逆に、ゼロ埋めされる実行を引くと問題が見えない。「今日は動いた」は保証にならない。

### 実測メモから取り込んだ結論
- **ズレ ≒ 起動遅延 + Σ(underrun による欠損)。** underrun 1回の回では差 -0.001秒で一致。
  時間比例の成分は見当たらず、**クロックドリフトではなかった**。ただしデバイスで符号が変わる
  （内蔵マイクは逆に「録れた長さ > 実経過」）ので一般則ではない。
- **60分テストの位置づけが変わった。** ドリフトの有無を調べる場ではなく、この式が
  1時間でも崩れないかを確認する場になる。
- **underrun は負荷で増える**（30秒で1回 → 10回）。両系統で発生時刻が一致する組があり、
  系統ごとではなくプロセス全体か OS 側の要因。**60分テストでは余計なものを走らせない。**
- 回り込みは USB ヘッドセットで **45.1 dB**（有線イヤホンの42.5dBより良い）。
- 録音音量は **-4.0 dB で運用**。+2.3 dB ではクリップ。余裕は2.2dBしかない。
- **3つ目のレートが出た**（H340 は 44100 Hz）。リサンプルは実行時に読んだ値で組む。

## 第4回実測（70分連続録音）の反映

### 確定したこと
- **クロックドリフトは無い。** ズレ ≒ 起動遅延 + Σ(underrun の欠損)。70分で1045回×6.9ms＝
  7.21秒に対し実測7.26秒。判定の決め手は「ドリフト換算は3回で9倍ばらつくのに、
  1回あたりの欠損は長い2本で10%差に収まった」こと。→ ADR-006。
- **ゼロ埋めは70分続く。** 穴は8個/81.8秒＝1.93%で、動画が止まっていた時間帯に固まっていた。
  ADR-004 は維持しつつ、`drops_sec_len` は「例外を拾う仕組み」と位置づけ直した。
- **70分の WAV は壊れない。** 自分405MB / 相手730MB。逐次書き出しは効いている。
  相手の RMS は70分ずっと -31±1 dBFS。運用の音量目安として REQUIREMENTS へ記録した。

### 直したもの（実測メモの分担どおり）
1. **バッファを既定から1秒へ**（`BufferSize::Fixed(rate)`、通らなければ既定へフォールバック）。
   cpal のソースのとおりコールバック周期は `GetDevicePeriod()` 固定なので、**遅延は増えず
   取りこぼしの余裕だけ増える**。停止後に処理するこのPJだから採れる手で、voice-input では採れない。
   **効果は未検証**。開発デスクトップでは1秒バッファが受理されることだけ確認した。
2. **先頭の空白を `drops_sec_len` に含めた。** 統合器が「サンプル0 = first_data_sec」と
   「それ以降の穴」の2つの原点を組み合わせる契約になっていたのを、`drops_sec_len` だけで
   復元できる形に変えた。誤差は約1バッファ。
3. **ズレの警告文言を系統で分けた。** 相手は「鳴っていた時間しか来ない」、自分は
   「起動遅延 + underrun」。同じ文言だと読み違える。実際に1回あたりの ms も出すようにした。

### 記録の整理
PROGRESS.md が59行/60行で上限に触れたため、**ADR を `docs/adr.md` へ移した**。
グローバル規約は「10件超で `docs/adr/`（1決定1ファイル）」だが、行数上限のほうが先に効いた。
7件なので単一ファイルにしている。増えたら分ける。

### STT の方針を決めた（ADR-007）
業務ノートの空きが3.4GB（うち今回の録音1.1GB）しかないため、**ビルドも Python も要らず
容量が最小の whisper.cpp ビルド済み CPU バイナリ**を第一手にした。
Vulkan 一式（SDK・Ninja・MSVC BuildTools・CMake）は数GB必要で入らない。
voice-input と同じエンジンなので結果が流用でき、速度が足りなければ GPU 化も同じ道を辿れる。

## 第5回: 文字起こしベンチ（業務ノート CPU）

**結論: 実時間比 3.353。要件（0.1）に33倍足りない。** 60分の会議に3.4時間かかる。
桁が違うのでチューニングで埋まる差ではない。詳細は NOTES.md「第5回」。

判ったこと:
- スレッドを増やすと遅くなる（`-t 4` 3.353 → `-t 14` 5.312）。ハイブリッド CPU で
  ggml のスレッドプールが最も遅いスレッドを待つため。**会議中に走らせるならむしろ好都合。**
- BLAS 版は効果なし。素の 8MB 版でよい。
- **精度は十分。**モデルを落とす道は CLAUDE.md の方針（速さのために精度を落とさない）で選べない。
- コア数で性能を推測してはいけなかった（U系15W・最大1.6GHz・大半が効率コア）。
- メモリは 945MB。**長時間音声のメモリ懸念は消えたまま。**

こちらで補ったこと:
- **実運用では2トラックぶん要る**ので素のままなら約2倍。VAD を入れれば2倍化は防げるが、
  33倍の側は動かない。VAD は幻聴対策として別途価値がある。
- **公式に Vulkan のビルド済みバイナリは無い**（Issue #3673 で要望中）。コミュニティビルドは
  あるが、会議の中身を扱う業務機で素性の分からないバイナリは走らせない。

記録の更新:
- 非機能要件の「30分あたり3分以内」に**未達であること**を明記した。
- 未決事項を「文字起こしをどこで走らせるか」「要約がいつ必要か」「VAD を入れるか」に組み直した。
- 「業務ノートで現実的か」は測定済みとして閉じた（現実的でない）。

**次は技術ではなく判断。**2段構えにするなら、会議の音声を業務ノートの外へ出してよいかの
判断が要る（所属組織のポリシー。CLAUDE.md のとおりユーザーが決める）。
