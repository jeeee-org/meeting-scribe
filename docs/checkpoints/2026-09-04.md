### 直したバグ: 相手トラックの右チャンネルを捨てていた
902,813フレーム中879,369＝97.4%で L≠R だったのに 1ch に落として書いていた。
最初のチャンクだけで判定しており、それが0.333秒に届いた**モノラルの合図ビープ**だった。

**窓を広げても直らない**ことに注意した。本編の再生開始が10秒後なので、5秒の窓でも同じ
誤判定になる。会議の音はシステム全体の再生音（通知音・動画が混じる）でモノラルの根拠が無い。
→ **相手側は構造的にダウンミックスしない**（`downmix_allowed = false`）。
→ マイク側は残すが、判定を「無音でないフレームが0.2秒ぶん、かつ2秒ぶん見てから」に変更。
   材料不足のまま打ち切った場合は落とさない（安全側）。
→ 表示の文言も修正。`downmix_violations > 0` で「全chが同一だったため」と書くのは記録が偽になる。

`timeline_sec_frames` を小数3桁へ（式が崩れた時に場所を追える解像度）。

### 検証中に出た新しい事実: ゼロ埋めは同じ機械でも実行ごとに割れる
改修後の動作確認で、**開発デスクトップの NVIDIA HDMI がゼロ埋めしなくなった**
（最初のデータが3.22秒＝再生開始と一致）。過去2回の実行では0.01/0.03秒から埋まっていた。

「直前まで再生していたからエンジンが回り続けていた」という仮説を立てて実験したが、
**音を鳴らした直後に無音のまま6秒録ってもフレームは1つも来ず、否定された**。
他アプリが再生ストリームを開いたままだったのが原因と考えられるが特定できていない。

→ **ドライバ別の整理（NVIDIA はゼロ埋め / Realtek は来ない）を撤回した。**
→ ADR-004（時刻ベース統合）は「機種によっては必要」ではなく**常に必要**。強化された。
→ 逆に、ゼロ埋めされる実行を引くと問題が見えない。「今日は動いた」は保証にならない。

### 実測メモから取り込んだ結論
- **ズレ ≒ 起動遅延 + Σ(underrun による欠損)。** underrun 1回の回では差 -0.001秒で一致。
  時間比例の成分は見当たらず、**クロックドリフトではなかった**。ただしデバイスで符号が変わる
  （内蔵マイクは逆に「録れた長さ > 実経過」）ので一般則ではない。
- **60分テストの位置づけが変わった。** ドリフトの有無を調べる場ではなく、この式が
  1時間でも崩れないかを確認する場になる。
- **underrun は負荷で増える**（30秒で1回 → 10回）。両系統で発生時刻が一致する組があり、
  系統ごとではなくプロセス全体か OS 側の要因。**60分テストでは余計なものを走らせない。**
- 回り込みは USB ヘッドセットで **45.1 dB**（有線イヤホンの42.5dBより良い）。
- 録音音量は **-4.0 dB で運用**。+2.3 dB ではクリップ。余裕は2.2dBしかない。
- **3つ目のレートが出た**（H340 は 44100 Hz）。リサンプルは実行時に読んだ値で組む。
