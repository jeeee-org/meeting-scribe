既存の `mtg-practice` と混ざらず、「録音」ではなく「記録を作る」という本体価値が名前に出るため採用。

## 作るものの整理
Slack / Teams の打ち合わせを、開始・停止のホットキー2つで記録し、要約テキストを自動生成する。
- 自分の声 = マイク、相手の声 = PC の再生音（WASAPI ループバック）を**別トラックで**録る。
  混ぜて1本にすると誰の発言か落ちるため、2系統の分離がこのPJの本体価値になる。
- 停止後に文字起こし → タイムスタンプで統合 → `自分:` / `相手:` ラベル付きトランスクリプト → LLM 要約。

## この時点で置いた設計上の判断（未確定・要検証）
- **voice-input とは要求が正反対**。あちらは体感レイテンシがすべて、こちらは正確さと要約の質。
  停止後に数十秒かかってよい代わりに、速さのために精度を落とす判断はしない。
- **最大のリスクは長時間音声**（60分超）。文字起こし時間・メモリ・LLM の入力上限が一気に効く。
  短い会議で動いても長い会議で壊れる、を前提に設計する。
- **会議内容の外部送信は既定でゼロ**にする（ローカル STT）。業務の会議を扱うため。
  録音・文字起こし・要約はリポジトリに入れない（`.gitignore` 済み・出力先はリポジトリ外）。

## セッション2: ループバック録音の実証と、方針の3件確定

### やったこと
1. **cpal がループバックに対応済みであることをソースで確認**。voice-input が既に使っている
   cpal 0.18.2 が、出力デバイスを入力として開くと `AUDCLNT_STREAMFLAGS_LOOPBACK` を立てる
   （`src/host/wasapi/device.rs:855`）。新しい依存も自前の WASAPI 実装も要らない。
2. **`proto/dual-capture` を作成**（Rust、約280行）。マイクとループバックを別 WAV に落とし、
   経過時間と実サンプル数のズレ・音量・コールバック数・エラー数を数字で出す。
   「録れるか」ではなく「タイムラインが保たれるか」を測るのが目的。
3. **無音時の挙動を実測** → 12秒中、最初の5秒は何も再生せずに測ってズレ +0.00 秒。
   無音区間もゼロ埋めで返ってくる。**最大の懸念だったリスクが外れた。**
   ただし開発デスクトップの NVIDIA HDMI 出力1つでの結果。業務ノートで再確認するまでは決着にしない。

### 決めたこと（ADR-001〜003 / PROGRESS.md）
- 実装言語は **Rust**（cpal 流用が実証できたため）
- **アプリ化しない**。対象PCがリポジトリを pull できるので `cargo run` で足りる
- **有線 / USB ヘッドセット運用を前提**にする（ネックスピーカーは不可）

### 認識を改めた点
- 「LLM の入力上限が効く」は**過大なリスク認識だった**。60分の会議は多く見ても2万字程度で
  200K コンテキストに余裕で収まる。残る本丸は**文字起こしの所要時間とメモリ**。
- 要約にサブスクの Claude を使う案が成立する。voice-input で「使わない」と決めたのは
  レイテンシ要件からで、**このPJには効かない前提**だった。

### ハマった点
- WSL から `cargo.exe` を起動しても `CARGO_TARGET_DIR` は渡らない（WSLENV 未経由）。
- 出力デバイスに `default_input_config()` を呼ぶと失敗する。`default_output_config()` で取る。
- WSL から `.exe` を起動すれば実オーディオデバイスに届いた（Windows プロセスとして走るため）。
  ループバック側の計測はこちらから回せる。

## セッション3: 業務ノートでの実測反映と、proto の 60分テスト対応

業務ノート（ThinkPad L13 Gen 4）での実測メモを受領して反映した。**このPCからは push できないため
内容をコピペで受け取る**、という運びだった。

### 反映した内容
- **NOTES.md の既存記述をひとつ訂正した。**「ループバックは無音でもパケットを返した」は
  開発デスクトップの NVIDIA HDMI 出力でしか成り立たず、業務ノート（Realtek）では逆だった。
  見出しに機種を明示し、結論部を「この読みは後に覆った」へ書き換えた。
  留保（「業務ノートで再実行するまでは決着にしない」）を付けていたことが効いた。
- 業務ノートでの実測を NOTES.md へ追記（無音時の挙動 / 回り込み42.5dB / エンドポイントの
  抜き差し / 録音音量27%の罠 / 内蔵マイク4chがモノラルの複製 / フォーマット差 / underrun /
  マイクの長さ超過 / Windows 側の環境構築の罠）。
- ADR-004（統合は時刻ベース）と ADR-005（エンドポイントは設定で固定）を追加。

### proto/dual-capture の改修（60分テストの前提条件）
実測フォーマット（自分48kHz×4ch / 相手96kHz×2ch）のまま60分回すと**メモリ約5.5GB**になり、
業務ノートで走らなかった。次の5点を入れた。

1. **逐次書き出し** — チャネル経由で書き出しスレッドへ流し、`hound::WavWriter`へ直接書く。
   メモリは平坦になる。音声コールバックで I/O を踏まないよう、スレッドを分けた。
2. **マイクの4ch→1chダウンミックス** — 最初のチャンクで全chの一致を確認してから落とす。
   決めた後にヘッダは変えられないので、**以降の破れはフレーム数で数えて報告**する。
3. **1秒ごとの累積フレーム記録** — ズレが「じわじわ開いた（ドリフト）」のか
   「一度に飛んだ（欠損）」のかを、最終サマリだけでは区別できないため。
4. **underrun の発生時刻を記録** — 回数だけでなく時刻を持ち、ズレと突き合わせられるようにした。
5. **`*-meta.json` サイドカー** — 採用したエンドポイント名・フォーマット・タイムライン・
   underrun 時刻・無通信区間を WAV と対で残す。

あわせて **`Chunk.at`（到着時刻）を使って「パケットが来なかった区間」を時刻付きで検出**する
機能を足した。到着時刻と既受信の音の長さの差が一段増えた点を拾う。ADR-004 で埋めるべき穴が
そのまま `drops_sec_len` に出る。

### 動作確認（開発デスクトップ・8秒）
逐次書き出し・タイムライン・meta.json・underrun時刻すべて動作。ズレ +0.02秒、
`drops` は空（NVIDIA はゼロ埋めするため期待どおり）。underrun は 0.026秒＝最初のコールバック。
