# dual-capture — 2系統録音の計測プロトタイプ

マイク（自分）と WASAPI ループバック（相手＝PC の再生音）を**別 WAV** に落とす。
**製品ではなく計測用**。「録れるか」ではなく**タイムラインが保たれるか**を数字で出すのが目的。

実行は **Windows 側のみ**（WSL では動かない）。編集は WSL から行ってよい。

---

## 実行環境

業務ノート（ThinkPad L13 Gen 4）は **セットアップ済み**。Rust・MinGW は導入され、
`run.cmd` が通ることを確認してある。新しい機械で一から入れる場合は
`NOTES.md`「Windows側の環境構築でハマった点」を先に読むこと（GNU ツールチェーンだけでは
`windows` クレートが通らない、`.ps1` は BOM 付き UTF-8、など）。

## 使い方

```
run.cmd --list                                デバイス一覧（名前を控える）
run.cmd 30                                    30 秒録る
run.cmd 3600 --mic=Logi --loopback=Logi       1時間、エンドポイントを名前で固定して録る
```

`--mic=` / `--loopback=` は**名前の一部**でよい（前方一致ではなく部分一致）。
**既定任せにしない**。ヘッドホンジャックのエンドポイントは抜き差しで一覧から消え、
既定が耳に届かないデバイスへ移る（ADR-005）。指定を忘れると1時間ぶんの無音 WAV ができる。

## 出力

カレントディレクトリに、実行ごとに次の4ファイル。**会議の中身に当たるので `.gitignore` 済み。**

| ファイル | 中身 |
|---|---|
| `dual-<epoch>-self.wav` | 自分（マイク） |
| `dual-<epoch>-other.wav` | 相手（ループバック） |
| `dual-<epoch>-*-meta.json` | 採用したエンドポイント名・フォーマット・計測値 |

`meta.json` の主な項目:

- `device` — **実際に掴んだエンドポイント名**。「無音だったのはなぜか」を追う起点
- `gap_sec` — 実経過 − 録れた長さ。**ここが本命の数字**
- `drops_sec_len` — `[時刻, 空いた秒数]` の配列。パケットが来なかった区間
- `underrun_sec` — underrun の発生時刻
- `timeline_sec_frames` — 1秒ごとの `[経過秒, 累積フレーム]`
- `downmixed` / `downmix_violations` — マイクを 1ch に落としたか、後から破れた件数。
  **相手側は落とさない**（システム全体の再生音はステレオ前提。先頭に来るのが合図音や
  通知音だとモノラルに見えて誤判定する。実際に右チャンネルを全部捨てたことがある）

## 新しい機材を挿したときの手順

ドライバが変われば挙動も変わる。**「実測した」は「その機種・そのエンドポイントで実測した」
でしかない**（NOTES.md）。機材を替えたら次の順で測り直す。

> **Logi H340 は 1〜3 を実施済み**（名前・音量 -4.0 dB・回り込み 45.1 dB）。
> 同じ機材で続けるなら **4 から**でよい。値は REQUIREMENTS.md「実機の構成」にある。

**1. 名前を控える**

```
run.cmd --list
```

**2. Windows の録音音量を確認する**

設定 → システム → サウンド → 入力 → 該当デバイス。**デバイスごとに別設定**なので、
前のデバイスで直した値は引き継がれない。過去に 27% のまま気づかず、
ピーク -48.7 dBFS しか出ていなかったことがある（NOTES.md）。

**Logi H340 は -4.0 dB（47.3%）で調整済み。** +2.3 dB ではクリップした。
この設定でも声を張ったときの余裕は 2.2 dB しかないので、挿し直したら録音前に確認する。

**3. 30秒の3段テストで回り込みを測る**

別ウィンドウで音を鳴らしながら、録音を1本走らせる。段の境界に
`powershell -c "[Console]::Beep(880,200)"` を鳴らすと、**両トラックに境界マーカーが残る**
うえ、話者が画面を見ずに済む。

| 段 | 0-10秒 | 10-20秒 | 20-30秒 |
|---|---|---|---|
| 自分 | 喋る | **黙る** | 喋る |
| 再生 | なし | **あり** | あり |

**見るのは段B（黙る・再生あり）のマイク RMS。** 回り込みは
「相手の音だけが鳴り、自分が黙っている区間」でしか測れない。
喋りながら鳴らす区間だけでは、マイクのエネルギーがどちらのものか分離できない。

**4. 60分の本番**

```
run.cmd 3600 --mic=Logi --loopback=Logi > 60min.log
```

**操作は要らない。**合図のビープも再生ループも不要で、開始したら放っておく。
むしろ**実際の会議を1本そのまま録るのが一番安い**（会議の音が鳴っている条件で測れる）。
録音以外に何を走らせていたかだけ控えておく。

ディスクは**合計 1〜1.8GB 程度**（自分側は 1ch に落ちるので約 0.35GB、相手側は
44.1kHz/2ch なら約 0.64GB、48kHz なら約 0.7GB、96kHz なら約 1.4GB）。

## 見る数字と目安

| 項目 | 目安 | 外れたときの意味 |
|---|---|---|
| マイクのピーク | **-12〜-6 dBFS** | 低すぎ＝録音音量。-6 超え＝クリップして文字起こしが荒れる |
| 段B のマイク RMS | 段A より **40dB 以上低い** | 差が小さい＝回り込んでいる。開放型で聞いていないか |
| 相手の `gap_sec` | 再生していた時間と一致 | 一致＝「再生中しかパケットが来ない」型。**同じ機械でも実行ごとに割れる**ので、毎回読む |
| 自分の `gap_sec` − `first_data_sec` | **`underrun_sec` の件数 × 約17ms** | 大きく超える＝式が崩れた。`timeline_sec_frames` の傾きで場所を探す |
| `underrun_sec` | 低負荷なら数回 | **負荷で増える**（30秒で1回→10回の実測あり）。開始直後の1回は無害の見込み |

## 60分テストで見る数字（2つに絞れた）

1. **`gap_sec` − `first_data_sec` が `underrun_sec` の件数 × 約17ms に収まるか。**
   ズレは「起動遅延 + underrun による欠損」で説明でき、時間に比例して伸びる成分は
   見つかっていない（NOTES.md）。1時間でもこの式が崩れないかを確認する。
2. **`drops_sec_len` が相手の無音区間を取りこぼさず拾えているか。**
   これがそのまま時刻ベース統合器の入力になる（ADR-004）。

**余計なものを走らせないこと。** underrun は負荷で増えるので、再生ループや頻繁な画面更新を
同時に回すと1の式が検証にならない。何を走らせていたかも併せて記録する。

## 結果の渡し方

**業務ノートからは push できない。** 実行後の標準出力（サマリ部分）と `meta.json` を
コピペで渡す。WAV そのものは会議の中身に当たるので**渡さない・コミットしない**。

`.exe` の標準出力をコンソール越しに読むと CP932 で化けるので、
**ファイルへリダイレクトしてから読む**のが確実。
